# SourceKit-LSP indexing for Xcode projects in Neovim

How `gd` / cross-module indexing is wired for the Notability iOS project (and any
`.xcodeproj`-based Swift project) using `sourcekit-lsp` + `xcode-build-server`,
plus how to keep it healthy. Config lives in [`lua/plugins/swift.lua`](./lua/plugins/swift.lua).

## The two layers

Xcode-parity navigation needs **both** of these to be healthy. They're independent
— one can be fine while the other is broken, which is what makes failures confusing.

| Layer | Powers | Where it lives |
|---|---|---|
| **Xcode index store** | Jumping *to* a symbol's definition/refs across modules | `DerivedData/<Project>-<hash>/Index.noindex/DataStore` |
| **`.compile`** | Type-checking the file you're *in* — the prerequisite for `gd`, completion, diagnostics, hover | repo root, next to `buildServer.json` |

`gd` is a two-step move: sourcekit-lsp first type-checks the open file (needs flags
from `.compile`) to resolve your cursor into a symbol, **then** consults the index
store to find where that symbol is defined.

## The #1 failure mode: missing `.compile`

If `.compile` doesn't exist, xcode-build-server returns "no flags" for **every**
file:

```
sourcekit: -32003: No workspace containing 'file:///.../SomeFile.swift' found
```

Result: no semantic features at all — **even same-file `gd` fails**, because the
LSP can't get far enough to type-check the file. The index store being fully
populated doesn't help; it's never reached. This is almost always the real cause
when "go-to-definition doesn't work anywhere."

## How `.compile` works

It's xcode-build-server's per-file compile-flag database, generated by **parsing a
build log**. So it's only ever as complete as the build it was parsed from:

- A **full build** of the umbrella scheme → flags for the whole graph.
- An **incremental build** → flags only for what recompiled (use `parse -a` to
  merge into the existing DB).

Structure: one whole-module entry per Swift module (modules with many files store
their source list in a `.SwiftFileList` response file rather than inline — that's
why grepping `.compile` for a specific `.swift` path can come up empty even though
it's covered), plus one entry per C/C++/ObjC file.

`-dry-run` does **not** work for generating it — it only emits a `swiftc --version`
probe, not per-file compile commands.

## Initial setup (one-time)

```sh
cd <repo-root>

# 1. Bind buildServer.json to the umbrella scheme (compiles all deps in one build).
#    For Notability the umbrella is the `Notability` scheme — there is no
#    aggregate "build everything" scheme.
xcode-build-server config -project ios/Notability.xcodeproj -scheme Notability

# 2. Full build -> complete .compile.
#    arm64-only: a generic simulator destination otherwise defaults to
#    ONLY_ACTIVE_ARCH=NO and builds arm64 + x86_64, doubling build time for
#    nothing. The index store is arm64.
xcodebuild -project ios/Notability.xcodeproj -scheme Notability \
  -destination 'generic/platform=iOS Simulator' -configuration Debug \
  ARCHS=arm64 ONLY_ACTIVE_ARCH=YES \
  clean build 2>&1 | tee /tmp/nb_build.log

xcode-build-server parse -o .compile /tmp/nb_build.log

# 3. Restart the LSP in nvim.
:LspRestart
```

For Notability this yields ~1,422 entries (154 Swift modules + ~1,268 clang files)
covering every GL framework, `Model`, `ModelUI`, `BezierKit`, and the app.

## Maintenance (cheap, ongoing)

After the one-time full build you **never need another clean build** unless
DerivedData is wiped. Refresh flags with an *incremental* build:

| Keybind | Action |
|---|---|
| `<leader>cxc` | Refresh `.compile` (incremental `xcodebuild build \| xcode-build-server parse -a`). Run after adding files, changing build flags, or a big rebase. Derives project + scheme from the nearest `buildServer.json`. |
| `<leader>cxi` | `workspace/triggerReindex` — re-scan the index store. |

After either, run `:LspRestart`. New files are mostly auto-covered without a
refresh via `XBS_FEAT_NEWFILE=1` (infers flags from sibling files in the same dir).

The equivalent of `<leader>cxc` by hand:

```sh
xcodebuild -project ios/Notability.xcodeproj -scheme Notability \
  -destination 'generic/platform=iOS Simulator' -configuration Debug \
  ARCHS=arm64 ONLY_ACTIVE_ARCH=YES build 2>&1 \
  | xcode-build-server parse -a -o .compile
```

## git hygiene

Both files hold machine-specific absolute DerivedData paths — never commit them.

- `buildServer.json` — already gitignored in the Notability repo (`*buildServer.json`).
- `.compile` — added to `~/.gitignore_global`.

## Troubleshooting

- **`-32003: No workspace containing '<file>'`** → `.compile` is missing or doesn't
  cover that file. Run `<leader>cxc` (or the full setup if `.compile` is absent),
  then `:LspRestart`.
- **`gd` jumps work into a module but not within a freshly-edited file** → the
  index store is stale for that file; `<leader>cxi` and/or rely on
  `--experimental-feature background-indexing` (already enabled in `cmd`).
- **Nothing resolves after `git clean`/Xcode "Clean Build Folder"** → DerivedData
  (index store + intermediates) is gone; redo the one-time full build.
- **`buildServer.json` points at the wrong scheme** → flag serving is actually
  scheme-agnostic (`.compile` drives it), but the scheme controls what a
  BSP-triggered build compiles. Keep it on the `Notability` umbrella.

## Verifying go-to-definition headlessly

To confirm without manual clicking, drive sourcekit-lsp over stdio: `initialize`
(rootUri = repo), `initialized`, `textDocument/didOpen` the file, wait for build
settings to resolve, then `textDocument/definition` at a symbol's position. A
non-null result with no `-32003` means the chain is healthy. (A throwaway Python
driver doing exactly this lives in chat history if needed again.)
